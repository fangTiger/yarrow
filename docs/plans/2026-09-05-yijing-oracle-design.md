## 1. 一句话

一个说错话就会死的预言家。

三位 AI 易者用易经为提问者占卜，但必须把模糊的卦辞**预注册**成带概率的可证伪命题，并以自己的金库为其背书。算错就赔给提问者，金库耗尽则**永久封存**，卦历留在链上作为墓志铭。

---

## 2. 核心论点

本项目**不主张**易经能预测未来。

真正的论点是：

> **任何模糊的预言系统，一旦被迫预注册具体结论并承担赔付责任，其任意性就会暴露。**

因此：
- AI 从爻辞推导出具体命题的过程**确实包含跳跃**，这一点在产品内公开承认，不做辩护。
- 易者破产是**预期结果**，不是 bug。
- 系统测量的不是"易经准不准"，而是**"含糊其辞的成本"**。

对外表述统一为：**"第一个愿意为每句卦辞开具赔付责任的易者。"**

不使用"千年以来第一个有胜率的占卜师"——该表述不可证实，且已被先例击穿。

不在任何对外材料中使用"易经千年不倒只因故意模糊"这类历史论断——易学具有严肃的哲学与解释学传统，该表述对懂行受众是冒犯性的浅见。

### 3.0.1 由实测导出的强制设计约束

**C1 — 所有截止一律使用区块高度，禁止使用时间戳。**
实测观察到连续两个区块时间戳完全相同（均为 `1788540867`）。官方文档：「Timestamps: 非递减，不严格递增 —— 用区块号排序」。

**C2 — USDC 为双接口双精度，必须全局统一。**
原生接口 18 位小数，ERC-20 接口 6 位小数，同一底层资产。金库记账、押注公式 `ΔB = m·F·(1−4(p−o)²)`、前端展示若混用，误差达 10¹²。
**决定：合约内部一律使用 ERC-20 接口（6 位）计价与记账。**

**C3 —（已降级为提示）零地址约束。**
向**零地址**转账被禁止，这一条仍然成立，合约需拒绝零地址收款人。
但「向全新零状态地址转账」与「合约余额完全清空」**经实测均可成功**，无需特殊处理。

**C4 — 不可依赖 EIP-1559 燃烧语义。**
Arc 基础费付给出块受益人，不燃烧；下一区块基础费发布在父区块头 `extra_data`。

### 3.0.2 Arc 原生 agent 标准（需在设计中表态）

Arc 原生提供：
- **ERC-8004**：agent 身份、声誉事件、凭证验证
- **ERC-8183**：任务全生命周期 —— 创建、托管注资、交付物提交、评估、USDC 结算

**ERC-8183 与本项目手搓的托管/结算存在功能重叠。** 必须在实现前决定是复用还是绕开，且 pitch 必须能回答「你为什么不用 ERC-8183」。

**已确认的 Arc Testnet 部署地址**：

| 合约 | 地址 |
|---|---|
| ERC-8004 IdentityRegistry | `0x8004A818BFB912233c491871b3d84c89A494BD9e` |
| ERC-8004 ReputationRegistry | `0x8004B663056A597Dffe9eCcC1965A193B7388713` |
| ERC-8004 ValidationRegistry | `0x8004Cb1BF31DAf7788923b405b754f57acEB4272` |
| ERC-8183 AgenticCommerce（**社区候选，非官方**） | `0x0747EEf0706327138c69792bF28Cd525089e4583` |
| USDC (ERC-20 接口) | `0x3600000000000000000000000000000000000000` |

**决定（已定，非倾向）**：

1. **复用 ERC-8004 IdentityRegistry** —— 三位易者注册为链上身份，可被第三方发现与调用。`register(string)` 铸造身份 NFT。
2. **复用 ERC-8004 ReputationRegistry** —— 每次结算后由**结算合约**写入 Brier 分数。
   注意 ERC-8004 规则：**agent 所有者不得为自己的 agent 记录声誉**。本设计天然合规，因为分数由结算合约按确定性规则写入，不由项目方手工提交。
3. **AttestedResolver 实现为 ValidationRegistry 的 validator** —— 「人层」判定走 `validationRequest` / `validationResponse` / `getValidationStatus`，而非自建签名通道。
4. **ERC-8183 不复用** —— 两个理由：
   - 语义不同构：其流程是「交付物提交 → 评估 → 释放托管」，与本项目「概率预测 → 恰当评分规则 → 连续赔付 → 金库封存」不匹配，强行复用会扭曲结算数学。
   - **实测发现官方未在 Arc Testnet 部署**：ERC-8183 官方规范与参考仓库未发布 Arc Testnet 地址；上表地址为社区候选（有代码 212 字节，`paymentToken()` 指向 Arc USDC），**不得作为官方部署依赖**。
   **pitch 中须明确给出此理由。**

**ValidationRegistry 链上实测（2026-09-05）**：目标地址为 EIP-1967 代理，`getVersion()` 返回 `2.0.0`，`getIdentityRegistry()` 返回上表 IdentityRegistry。实际函数签名为 `validationRequest(address,uint256,string,bytes32)`、`validationResponse(bytes32,uint8,string,bytes32,string)` 与 `getValidationStatus(bytes32)`；agentId 891440 的所有者调用请求成功，非所有者调用以 `Not authorized` 回滚。最终 `AttestedResolver` 真实流程已写入 response=100、tag=`yijing-outcome-v1`，并在截止块后解析为 `YES/decided`。证据见 `reports/arc-validation-e2e-2026-09-04T21-27-01-839Z.md`。

### 3.0.3 与 ERC-8004 声誉危机的关系（叙事支柱）

已发表的实证研究（arXiv 2606.26028，Ethereum/BSC/Base，2026-01-29 至 05-13，17.3 万 agent / 15.5 万条反馈）显示 ERC-8004 声誉层存在系统性失效：

- **98.7%–100% 的反馈既无支付凭证也无任务链接**；仅 1.2% 填写 `proofOfPayment`；仅 6.2% 的评价者有任何 x402 支付记录
- 73.5% / 59.2% / 90.6% 的评价者存在共同出资方聚类（女巫）
- 剔除女巫后，15.8% / 77.9% / 86.8% 的被评 agent 剩下**零条有效反馈**
- 算术平均聚合导致 **breakdown point = 0**，操纵中位成本 $0.0027
- **ValidationRegistry 在所研究的主网上无部署**

**本项目写入 ReputationRegistry 的每一条反馈，其凭证是一笔已结算的真实赔付。** 这构成与上述生态现状的直接对照，且 Arc Testnet 上 ValidationRegistry **确实已部署**，使「人层」判定可走标准通道。

叙事表述：
> ERC-8004 的声誉层目前塞满了零凭证的刷分记录。本项目写进去的每一条，背后都有一笔真金白银的赔付。

## 5. 起卦机制

### 5.1 仪轨与技术同构

传统起卦为**三枚铜钱掷六次**，本质即随机数生成。commit-reveal 的"先立誓、后开卦"与占卜仪轨天然同构，非技术妥协。

### 5.2 流程

```
① commit   提问者提交 H(question, salt, sender, roundId, chainId, contract)
           同时锁定卦金 F 与保证金 D（不可退）
② 等待     等待 N 个区块（N 固定，远小于 8191）
③ reveal   提问者揭示 question 与 salt
           seed = keccak256(salt, blockhash(commitBlock + N))
④ 成卦     由 seed 派生六爻
```

### 5.3 六爻派生

自 seed 取 18 bit，每爻 3 bit 对应三枚铜钱（正面=3，反面=2）：

| 三钱之和 | 爻 | 含义 |
|---|---|---|
| 6 | 老阴 ⚋ | 变爻 |
| 7 | 少阳 ⚊ | 静 |
| 8 | 少阴 ⚋ | 静 |
| 9 | 老阳 ⚊ | 变爻 |

由六爻得**本卦**；变爻反转后得**之卦**。

### 5.4 安全约束

| 攻击 | 对策 |
|---|---|
| 选择性揭示（看结果决定揭不揭） | **不揭示即弃卦**，卦金与保证金没收归金库。仪轨表述：「占而不诚者，其筮不告」 |
| 批量 commit 刷卦 | 保证金 D 须覆盖弃卦的期望收益；单地址每轮限额 |
| proposer grinding | 使用 commitBlock + N 而非紧邻下一块；单轮最大赔付严格封顶 |
| 问题哈希字典攻击 | commitment 强制含高熵 salt |
| 历史哈希过期 | 经 EIP-2935 合约读取，窗口 8191 块 ≈ 70 分钟；揭示窗口固定且远小于此；超时走明确的弃卦路径 |
| 用户与 proposer 串谋 | 单轮赔付封顶；Testnet 环境下经济激励不成立 |

**明示**：本随机源适用于低额仪式性用途，不适用于高额博彩。该结论写入 README 与 pitch。

### 5.5 花钱改命（动爻）

提问者可付费改变指定一爻，得新的之卦，易者重新解卦并重新预测。

**约束：动爻必须发生在易者提交 PredictionSpec 之前**，避免与已锁定的押注冲突。

叙事价值：你花钱改了命，易者反而可能更没信心（p 向 0.5 收敛）。

## 6. 预测与结算数学

### 6.1 易者输出

```
PredictionSpec {
  roundId
  direction      // YES / NO
  probability p  // [0.01, 0.99]，主观概率
  predicateId    // 必须来自 PredicateRegistry 白名单
  params         // 谓词参数
  deadline       // 截止块高（禁用时间戳，见 C1）
  reasoning      // 自然语言解卦（不参与结算）
  modelId        // 固定并记录
  promptHash     // 固定并记录
}
```

**易者不决定金额。** 金额由链上确定性公式计算。

### 6.2 身銭倍率 m

由确定性代码计算，**不经过 LLM**：

```
m = clamp( kelly(historicalBrier) * B / F , m_min , m_max )
```

其中 `kelly()` 为基于历史 Brier 分数的 Beta 后验风险比例。金库越厚、历史越准，敢押越重。

### 6.3 结算函数（恰当评分规则）

设结果 `o ∈ {0, 1}`，易者金库变动：

```
ΔB = m · F · ( 1 − 4·(p − o)² )
```

**性质验证**：设易者真实信念为 q，期望收益

```
E[ΔB] = m·F·( 1 − 4·[ q(1−p)² + (1−q)p² ] )
d/dp  = m·F·( 8q(1−p) − 8(1−q)p ) = 8·m·F·(q − p)
```

在 `p = q` 处取极大 → **报告真实概率是唯一最优策略**。

**关键行为**：

| 策略 | 结果 |
|---|---|
| 报准（p→o） | 赚 `m·F` |
| **报 50% 对冲** | **恰好赚 0** → 长期归零饿死 |
| 报 99% 预测必然事件 | 收益趋近 `m·F`，但因命题难度约束与同题对比而无优势 |
| 报高概率后翻车 | 亏至 `−3·m·F` |

这同时堵死了两个原始设计的致命漏洞：
1. 原公式 `EV = pF − (1−p)S` 导致理性 AI 永远押最小注 —— 已消除。
2. 一味对冲白拿卦金 —— 已消除。

### 6.4 资金预留

最大损失为 `3·m·F`，故开卦时从金库预留 `S_reserved = 3·m·F`。

预留不足 → 该易者本轮不得应卦。

### 6.5 计分

- 主指标为 **Brier 分数**，非胜率。
- UI 同时显示：样本量 n、Wilson 95% 置信区间。
- **三位易者必须预测同一个命题**，否则难度成为混杂变量、分数不可比。
- 「未决之卦」在计分中记为惩罚，防止易者靠乱质疑逃避赔付。

## 7. 三层判定：产品改为問／賭双轨

三层仍描述事实的信任来源，但不再把三层都伪装成同一种用户流程。入口先由一个与三位易者完全分离的中立分类器判断：**这个问题是否会在未来出现单一、可观察的答案**。分类器不读取卦象、易者输出、概率、押注额或候选链上谓词；结果必须由用户确认，用户可否决并切换轨道，原问题不得被改写。

| 产品位置 | 问题类型 | 判定与随机源 | 资金 | 信任假设 |
|---|---|---|---|---|
| **問轨（地层）** | 「我该不该辞职」「他到底怎么想」「今年会顺利吗」等没有唯一未来答案的问题 | 只读公开区块哈希，与规范化原问题共同派生六爻；三位易者只作解释，不作事实判定 | **不连接钱包、0 签名、0 交易、0 gas、不押注** | 解读是主观镜子，没有人替提问者作决定 |
| **賭轨（人层）** | 「今天之内会不会收到消息」「本周会不会和好」「本月能否拿到 offer」等有时间边界和可观察结果的问题 | 保留一笔立誓签名；命题保持用户原话，到期由提问者见证并接入 `AttestedResolver`，`MutualResolver` 作双边备选 | 三家押钱，沿用既有赔付流程 | 人类见证不是 trustless；冲突或缺席即未决 |
| **证据页（天层）** | Arc USDC 总量、agent 计数 | 保留既有 resolver、1000 回合 backtested 数据与 BSS、Wilson、配对置换检验 | 不进入新用户主流程 | 只证明机制、计分与统计管线被验证过，不证明易经或模型有预测力 |

問轨确认页必须逐句呈现项目的责任边界：

> 你问的这件事，没有一个将来会揭晓的答案。  
> 所以没有人能为它负责——**包括所有收过你钱的算命先生。**  
> 我们仍然可以为你解这一卦。

这不是降级提示。它是地层在个人尺度上的完整产品表达。問轨后端必须只依赖公开区块读取与解释器，启动或请求时均不得初始化钱包驱动；给定区块哈希和原问题，六爻必须可复算。

賭轨将演示与真实时间诚实拆开：短周期问题可在现场完成立誓、三家押注、提问者见证和人层结算；几天到几周的长周期问题停在“等待真实截止”，之后回到卦历见证，不以缩短区块窗口伪造已经发生的人间事实。卦历同时保留已结算人间事作为真实赔付证据，并把天层历史明确标成 `天层・backtested・非现场`。

#### 7.1.2 天层重新定义：占卜这条链自己的时势

**设计决定**：天层的判定对象从「外部市场价格」改为「**Arc 自身的链上状态量**」。

要求不变：合约可直读、提问者不可廉价操纵、结果真正不确定。

候选谓词（已实测可读性）：

| 谓词 | 数据源 | 实测 | 提问者可操纵性 |
|---|---|---|---|
| Arc 上 USDC 总量在块 H 前是否超过 X | `0x3600…0000` `totalSupply()` | ✅ 可读，当前 314,986,890,652.404 | 极低（需铸造/销毁上亿量级） |
| ERC-8004 注册 agent 数 | IdentityRegistry | ⚠️ 无计数接口，但 **`ownerOf()` 探测方案待验**（见 7.1.5） | 低（注册需付 gas 且公开可见） |
| 区块 gas 用量 / 网络活跃度 | `block.gaslimit` / `block.basefee` | ⚠️ 合约只能读当前块；`baseFee` 当前恒为 20 Gwei 下限，**不确定性为零，不可用** | — |

**采用**：USDC 总量与 ERC-8004 agent 注册计数均作为天层谓词。后者不依赖计数 getter，而由 `ownerOf(id)` 的存在性单调谓词二分恢复，实测与部署证据见 7.1.5。

#### 7.1.5 已验证：用 `ownerOf()` 探测恢复 agent 计数谓词

**此前判死的理由不完整。** ERC-8004 IdentityRegistry 无计数接口属实（九个候选选择器全部回滚），但它是 **ERC-721**，而 **`ownerOf(id)` 对不存在的 token 会 revert**——因此合约可用 `try/catch` 判定某 id 是否存在。

已注册的三个 agentId 为 **891440 / 891441 / 891442**（连号），说明 id 自某基数顺序递增。**在链上对 id 空间做二分搜索即可得出当前高水位 = agent 总数**，约 20 次 staticcall，gas 低廉。

**若验证通过，天层恢复第二个谓词**：

> 「Arc 上注册的 agent 总数是否会在块 H 前超过 N」

**为何优于 USDC 总量**：三位 AI 易者占卜的对象，成为它们自己所属的那个 agent 世界的命运——直接呼应第 3.0.3 节的叙事支柱。且「操纵该谓词」意味着必须真实注册 agent、真实扩大这个经济体，在叙事上是加分而非漏洞。

**2026-09-05 实测结论：可行，已实现并注册为天层谓词。**

- `ownerOf(0)`、`ownerOf(1)`、`ownerOf(891439..891442)` 均返回非零所有者；当前首个未铸造 id 的调用回滚，不返回零地址。
- 探测时高水位为 `891694`、首个缺失为 `891695`，零基计数为 `891695`；对 `891400..891694` 共 295 个 id 逐一检查无空洞，并在 `0..891694` 全区间等距抽样 65 个 id，无缺失。
- 链下二分需 19 次 `ownerOf`；`AgentCountResolver` 采用固定上界 `2^24`，含上下边界检查共 26 次。部署后 `currentCount()` 的 `eth_estimateGas` 为 `126134`。
- 最小无参数 `register()` 估算 `108899 gas`；按探测时 `25 gwei` 计，每新增一个 agent 最低约 `0.002722475 USDC`。把阈值推进 10 / 100 / 1000 分别至少约需 `0.027224750 / 0.272247500 / 2.722475000 USDC`，未含带 URI/metadata 的更高成本。
- 观察窗口内从 agentId `891442` 增至 `891694`，252 次注册用时 28,512 秒，即约 31.82 次/小时；按此速率推进 1000 约需 31.43 小时。该速率只是一次观察，不是未来承诺。
- `AgentCountResolver` 已部署为 `0x7332b3acc2b1533081558a01e63bbfae7141db0b`；谓词 `AGENT_COUNT_ABOVE` 已以 `HEAVEN`、`querentControllable=false`、`enabled=true` 注册。真实 `resolve` 交易 `0x23d30e262edad3f9e4a4909ead29666c0fa3f044e075e8c2343cf8cbe75a9bef` 实耗 `174316 gas / 0.004357900 USDC`，观察计数 `891702` 并成功缓存。

完整探测与链上验收分别见 `reports/arc-agent-count-2026-09-05T03-02-55-618Z.md` 与 `reports/arc-agent-count-e2e-2026-09-05T03-12-06-207Z.md`。

**限制**：上述可行性依赖当前官方 v2.0.0 实现使用 `_lastId++`、从 0 连续铸造且没有公开 burn。IdentityRegistry 是可升级代理；若未来升级加入销毁、跳号或起始规则变化，存在性将不再单调，resolver 会给出错误高水位。上链使用前必须把版本与实现不变量纳入运维监测。

#### 7.1.4 「块 H 时刻的状态」不可回读——已知张力与处理

普通 EVM 合约**无法在 H 之后回读「H 块时的 USDC 总量」**——`totalSupply()` 只返回当前值。这与第 7.2 节所述「EVM 读不到历史事实」是同一类约束，在天层同样成立。

**处理方式（已实现）**：resolver 记录**首次允许结算时的实际观察块与观察值**，并设置最大延迟上限；超过上限则返回**未决**，而非伪造成历史快照。

**代价与缓解**：谓词的真实语义是「H 之后首次观察到的值」而非「H 时刻的值」。在 Arc 0.51s 出块 + 无许可结算入口下，首次观察通常紧随 H 之后数秒，偏差可接受。**此语义须在 UI 与 pitch 中如实标注，不得表述为「H 时刻的快照」。**

**文化自洽性**：易所问者本为「时势」，非具体数字。「这条链在长还是在缩」正是时势。三位易者占卜的对象，是它们自己所处的这个链上世界的命运——这比预测外部币价更贴合易的本义，也更贴合「AI 在为链上世界占卜」的叙事。

**诚实代价**：本层的题材丰富度低于价格预测。须在 pitch 中承认这是外部预言机不可用下的选择，而非最优选择。

#### 7.1.3 可恢复路径（需人工操作）

若取得 **Pyth / Hermes API key**，价格谓词可恢复。但仍需先解决 Arc alpha 部署拒绝当前 VAA 的问题（可能需等待 Circle 更新该部署，或改用 Pyth Pro 订阅）。

**固定时点结算的正确 API 是 `parsePriceFeedUpdates`**，而非「先 update 后 getPriceNoOlderThan」——此结论保留，供恢复时使用。

**权限**：`updatePriceFeeds` 本身无白名单，任何地址可调用。但「谁能触发结算」取决于本项目 `update+settle` 入口的设计，需自行保证无许可。

### 7.2 为何天层仍作为证据存在

原设计的"纯链上事实"存在两个不可修复的问题：

1. **EVM 合约读不到**：无 opcode 可读取任意账户历史 nonce、回溯任意历史日志、判断"期间曾触及某价格"。这些仅在 JSON-RPC 层可查。
2. **提问者可操纵**：若命题涉及提问者可控的地址或合约，他只需做与预测相反的动作即可确定性抽干金库。

**天层自身状态谓词为机制试验同时解决二者**：合约可直读，且提问者难以廉价操纵。因此它仍是验证 resolver、计分和赔付的硬证据，但不再替代用户的人间问题。

### 7.3 未决之卦

「人层」ValidationRegistry 在截止前无有效响应，或低信任双边备选中双方声明不一致时，进入 `UNRESOLVED` 永久状态：

- 卦金与预留押注均不释放给任一方
- 该轮在 ScoreBook 中记为惩罚
- 链上永久标记

**博弈性质**：提问者说谎的收益为押注额，代价为保证金 + 卦金；保证金设定须使 `D ≥ S`，令说谎不获利。易者滥用质疑则自损 Brier 分数。

叙事价值：「未决之卦」比强行判定更符合占卜传统。

### 7.4 谓词白名单

`PredicateRegistry` 维护可用谓词类型。**LLM 不得自行发明 resolver**，只能从白名单选择并填参数。

每个谓词声明：
- resolver 合约地址
- 参数 schema
- 提问者可控性标记（`querentControllable`）
- 所属判定层

`querentControllable == true` 的谓词禁止进入天层押注。

### 7.5 AttestedResolver

「人层」主路径不自建 EIP-712 签名恢复通道，直接接入 Arc Testnet 的 ERC-8004 ValidationRegistry：

1. agent 所有者调用 `validationRequest`，把请求绑定到 `AttestedResolver`、agentId、URI 与 requestHash；Registry 自身执行 agent 所有权校验。
2. 任意地址可在 resolver 中登记与该请求严格匹配的案件和区块截止；不存在、已被响应或指向其他 validator 的请求均拒绝。
3. 白名单人类判定者在截止前调用 `submitOutcome`；resolver 以 validator 身份调用 `validationResponse`，YES 写 100、NO 写 0，并固定 tag=`yijing-outcome-v1`。
4. 截止后 `resolve` 重新读取 `getValidationStatus`，同时校验 validator、agentId、tag 与更新时间；缺席、非 0/100 或不匹配一律返回未决。

`MutualResolver` **不被删除，但不与 AttestedResolver 混为同一信任等级**：前者是双方自愿声明的低信任/演示备选，分歧即未决；后者是人层标准主路径，提供 ERC-8004 可发现、可索引的验证轨迹。Registry 只标准化「谁请求、谁响应、响应是什么」，并不把白名单人类判定者变成 trustless oracle；README 与 pitch 必须继续披露这一信任假设。

## 9. 死亡与封存

- 金库 `B < 3·m_min·F` → 无法预留 → 该易者进入 `SEALED` 状态
- 封存**永久且不可逆**，无复活路径
- 卦历、Brier 曲线、最后一卦保留在链上作为墓志铭
- 前端设独立的"墓域"展示已封存易者

**这是本项目相对所有先例的唯一真实差异点**，应作为 pitch 主轴而非彩蛋。

### 9.1 Arc Testnet 真实封存证据（2026-09-05）

已在独立单易者演示栈完成一次**由真实结算损失自然触发**的永久封存；未调用任何管理函数写入状态。参数为 `F=0.005000 USDC`、`m_min=1`、`m_max=5`、初始金库 `0.130000 USDC`，生存线为 `0.015000 USDC`。

一次 99% 正确预测把确定性倍率预热到 5；紧接着第一次 99% 错误预测的 Brier 为 `0.9801`，金库由 `0.134998` 降至 `0.061988 USDC`。策略随恶化记录把后续倍率收缩到 1；再连续四次相同 Brier 的错误结算后，金库依次降至 `0.047386 / 0.032784 / 0.018182 / 0.003580 USDC`，最后一次结算触发 `SEALED`。

封存后的再次应卦和正式 `deposit` 均以 `VaultSealed()` 回滚。即使绕过金库接口、直接强制转入一个 ERC-20 最小单位，状态仍为 `SEALED`，再次应卦继续回滚；因此未发现可复活路径。链上保留 6 条 ScoreBook 卦历与最后一卦（roundId 5），前端墓域只读复核后展示该墓碑。

完整 46 笔交易（43 笔成功、3 笔预期回滚）的哈希、块高、gas、资金轨迹与限制见 `reports/arc-seal-demo-2026-09-04T23-03-53-894Z.md`；部署清单见 `deployments/arc-testnet-seal-demo.json`。

## 10. 回放引擎（Walk-Forward Replay）

### 10.1 必要性

数十次样本的胜率在统计上不可读：30 次中赢 18 次，Wilson 95% 区间约为 42%–75%，与随机不可区分。核心机制若仅靠现场几卦，只能口头描述。

### 10.2 方法

1. 选取历史区块区间
2. 模拟 100+ 回合，以历史区块哈希为随机源起卦
3. 每回合**严格只提供截止块之前的信息**给易者
4. 以后续区块的真实数据结算
5. 三位易者预测**完全相同**的标准化问题
6. 结果带真实时间戳写入 ScoreBook

### 10.3 诚实标注（强制）

- UI 上明确标注 `backtested`
- 同时显示样本量与置信区间，不只显示胜率
- 不得将回放数据冒充为现场历史

**说明**：回放证明的是**机制在运转**，不是**易经有预测力**。诚实展示"样本不足"符合本项目祛魅的主题。

### 10.4 bankroll 更新

必须由确定性代码执行（Beta 后验 + 最大风险比例）。

**禁止**让 LLM"反思后决定少押"——那是事后编故事，不是校准。

### 10.5 首次完整回放结果（2026-09-05）

- 历史窗口：Arc Testnet 块 `60474233` 至 `60475039`；101 回合，截止块步长 8，结算跨度 6 块。
- 三家每轮共享同一冻结命题：「结算块的 USDC 总量是否严格高于截止块已知总量」。
- 预测阶段只接收截止块、截止块哈希、截止前历史、当时 USDC 总量和此前 Brier 状态；三家全部返回后才允许数据源读取结算块。
- 由于 Arc 时间戳按秒记录，2 块跨度曾被严格因果校验拒绝（块高更晚但时间戳同秒）；最终保留严格 `resolutionTimestamp > cutoffTimestamp`，把跨度增至 6 块，没有放宽校验。

#### 成本与样本量升级

- 1000 回合 × 3 易者约 **$0.932 / 6.99 CNY**；谷时约 **$0.466 / 3.50 CNY**
- actual 组直接复用主回放、另三组各 1000 时，四组总计峰时约 **$3.73 / 27.98 CNY**；谷时约 **$1.87 / 13.99 CNY**

### 11.2.6 重试规则（取代原 `maxRetries: 0`）

Anthropic 服务端 schema 约束不再适用；DeepSeek JSON 模式存在返回畸形 JSON 的可能。原 `maxRetries: 0` 会导致轮次失败。

**区分两类重试：**

| 类型 | 判定条件 | 是否允许 |
|---|---|---|
| **解析/schema 失败后重试** | 上一次输出**不是合法 JSON 或不满足 schema** | ✅ 允许 |
| **拿到合法输出后再生成** | 上一次输出**合法** | ❌ **禁止——此即择优** |

允许者须同时满足三条硬规则：

1. **首个合法输出必须被采用**，不得为求更优结果而继续生成
2. **每次尝试的原始输出哈希全部写入审计日志**
3. **尝试次数上链**

依据：重试一次失败的解析，与在多个合法结果中挑选，不是同一件事。前者不改变输出分布，后者改变。验证者可从链上尝试次数与日志哈希核对我们未在合法结果中择优。

**HTTP 层传输错误（超时、5xx、连接失败）视同未产生输出**，可重试，同样记录。

## 13. 合约接口草案

```solidity
enum RoundState { COMMITTED, REVEALED, PREDICTED, SETTLED, FORFEITED, UNRESOLVED, CANCELLED }
enum DivinerState { ACTIVE, SEALED }

struct Round {
    bytes32 commitment;
    address querent;
    uint64  commitBlock;
    uint64  revealDeadline;
    uint256 fee;            // F
    uint256 bond;           // D
    bytes32 seed;
    uint8[6] lines;         // 6/7/8/9
    uint8   primaryHex;     // 本卦
    uint8   derivedHex;     // 之卦
    RoundState state;
}

struct Prediction {
    uint256 roundId;
    address diviner;
    bool    direction;
    uint16  probabilityBps; // p，基点
    uint16  multiplier;     // m，由合约计算
    uint256 reserved;       // 3*m*F
    bytes32 predicateId;
    bytes   params;
    uint64  deadline;       // 块高，禁用时间戳（C1）
    bytes32 modelId;
    bytes32 promptHash;
}

interface IResolver {
    function resolvable(bytes32 predicateId, bytes calldata params, uint64 deadline)
        external view returns (bool);
    function resolve(bytes32 predicateId, bytes calldata params, uint64 deadline)
        external returns (bool outcome, bool decided);
}
```

| 合约 | 职责 |

| `DivinerVault` | 每位易者的金库、结算、封存 |
| `PredicateRegistry` | 谓词白名单、可控性标记、resolver 路由 |
| `ScoreBook` | Brier 记账、样本量、置信区间、卦历 |

Anthropic SDK 默认 `maxRetries: 2`。**自动重试会产生多次生成，破坏第 11.2 节「输出立即签名上链、杜绝多次重跑择优」的保证。**

### 15.6.2 ✅ 链上三家法定人数与超时作废（已修）

`PredictionBook` 在首笔成功预测时冻结当时全部 `ACTIVE` 注册易者；同轮所有预测仍由 `RoundTerms` 强制共享 predicateId、params 与 deadline。`settle` 在读取 resolver 之前检查冻结集合，缺席时以 `QuorumNotReached(roundId, submitted, required)` 回滚，链下编排器不再是安全边界。轮中后来注册的新易者不追溯加入，避免管理员以注册动作恶意改变正在进行的轮次。

**封存规则**：已提交者无论之后是否封存都计入；冻结集合中尚未提交、但金库已进入永久 `SEALED` 的易者免除本轮义务。理由是永久封存者已不可能再合法提交，让其继续计入只会把所有既有轮次永久锁死；封存前已经提交的承诺则不能被抹掉。

**超时规则**：

- 至少一家已提交：冻结 deadline 后任何人可调用 `cancelIncompleteRound`；整轮进入 `CANCELLED`，卦金与剩余保证金退还提问者，PredictionBook 中的奖励抵押退还，易者金库预留释放，且不写 Brier 样本。
- 零家提交：尚无可冻结的预测 deadline，因此以该轮既有 `revealDeadline` 为边界；窗口结束后同样允许任何人作废并全额退款。

选择退款而非没收，是因为缺席方不受提问者或已提交易者控制；没收会给缺席易者一个可低成本 grief 其他参与者的手段。代价是该轮没有分数与收益，但不会永久卡死，也不会把不可比的不完整样本混入排名。

TDD 先证明旧实现可在三家注册、仅一家提交后结算；修复后该测试与零提交超时测试均转绿。最终部署 `PredictionBook=0xc6c6465d314709f6620d8c5a178fd9369edf36f5`。真实链上反例观察到 submitted=1、required=3，`settle` 以 `QuorumNotReached` 回滚，第三方随后作废并释放全部本轮托管/预留；三家完整 mock agent 路径也再次结算成功。证据见 `reports/arc-quorum-e2e-2026-09-04T21-33-38-603Z.md` 与 `reports/arc-agent-e2e-2026-09-04T21-35-07-638Z.md`。

### 15.7.2 对 pitch 主轴的修正（重要）

**换用真实 LLM 后，结果大概率仍然如此。** 而这正是本项目的论点（第 2 节）：模糊预言被迫可证伪化后，暴露的是它的任意性。

因此 demo **不得**承诺「看这个 AI 越来越准」——那既不会发生，也与论点相悖。

**正确的叙事**：
> 看一个预言家被迫为每句话付钱之后会怎样——答案是慢慢破产，因为那里从来就没有信号。

「胜率曲线会因被打脸而学乖」这一预期（原第 6.5 节与 15.5 节的暗示）应当**降级为观察项而非承诺**：确定性 bankroll 策略确实会随 Brier 恶化而收缩身銭倍率 m，但这体现的是**风险管理在生效**，不是**预测能力在提升**。二者在 pitch 中必须区分清楚。

## 15.9 谓词难度缺陷与修复（2026-09-05，DeepSeek 校准发现）

### 15.9.1 20 回合校准暴露的测量退化

首轮 DeepSeek 真实推理校准结果：三位易者命中率 **90% / 90% / 80%**，Brier 0.187 / 0.175 / 0.220。

**此为假象。** 20 轮中 19 轮结果为 NO，**基础概率约 5%**。三位易者普遍报 30–64%（多数约 42%），方向自然全为 NO——闭眼说「不会发生」即可获得 95% 命中率。

**根因**：恰当评分规则挡住了「易者自己挑简单命题」，但**未挡住「命题编译器生成简单命题」**。防御建在了错误的位置。

### 15.9.2 参照系错误：0.25 不是本场景的正确基准

Brier 0.18 相对 0.25 看似良好，但 0.25 是「永远报 50%」的基准。正确参照为「永远报经验基础概率」的常数预测：

```
基础概率 p₀ = 0.05
参照 Brier = p₀(1−p₀)² + (1−p₀)p₀² = 0.0475
Brier Skill Score = 1 − 0.18 / 0.0475 ≈ −2.8
```

> **三位易者显著劣于一个只知道基础概率、别的什么都不懂的常数预测。**

此结论比原「Wilson 区间横跨 50%」更锋利且更定量，应作为第 2 节论点的主要量化证据。

**强制要求**：所有报告与 UI 除原始 Brier 外**必须同时给出 BSS 与该批次实际 YES 占比**；并明确标注**极端基础概率下命中率是误导性指标**。

### 15.9.3 修复：命题编译器难度校准（已实测生效）

`PropositionCompiler` 选择谓词阈值时，以严格早于截止块的历史窗口估计越过频率，反解出使经验基础概率接近 50% 的阈值。

实测结果：

| 项 | 值 |
|---|---|
| 历史基础概率区间 | **48.44% – 53.13%** |
| 全部轮次落入 35–65% 目标区间 | ✅ |
| 实际实现 YES 占比（n=20） | 40% |
| 校准历史窗口 | 60507474–60507984（截止块 60507985 **之前**） |

**前视偏差防护未被破坏**——校准所用历史严格早于该轮截止块。
