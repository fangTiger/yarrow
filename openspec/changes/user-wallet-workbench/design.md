## Context

合约在 `commit` 中通过 ERC-20 `safeTransferFrom(msg.sender, ...)` 扣取卦金和保证金，因此真正的提问者必须既是授权者也是 `commit` 的发送者；`reveal` 又要求同一提问者完成。三位易者拥有独立项目方金库，预测仍应由服务端隔离的三把 agent 私钥签署。Arc 的原生 USDC 为 18 位而 ERC-20 USDC 为 6 位，两种余额不能混用。

## Goals / Non-Goals

**Goals:**

- 浏览器通过注入钱包签署全部用户交易，服务端只签三位易者预测。
- 一次“求卦”动作启动整个编排；钱包确认是交易安全边界，不再出现产品中间步骤按钮。
- 在一个视口内看见当前位置、下一动作、卦象、三家状态、倒计时和最终裁决。
- 保留全部诚实披露、六秒仪式、倒计时和朱红“决”印。

**Non-Goals:**

- 不改合约、部署和 `.env`。
- 不执行真实 DeepSeek、回放或消融。
- 不为浏览器引入或派生任何私钥。

## Considered Approaches

1. **继续由服务端代签，只在前端伪装钱包。** 改动最小，但违反 `msg.sender` 所有权和用户付 gas 的目标，拒绝。
2. **把全部流程搬到浏览器。** 用户交易自然，但会迫使三位易者私钥进入浏览器，违反秘密隔离，拒绝。
3. **浏览器签用户交易，服务端准备/核验并签 agent 预测。** 选用。服务端生成 commitment 所需公开参数并核验回执，浏览器顺序签名，预测仍走现有 agent 编排。

## Decisions

1. **准备—单签名—自动揭示协议。** `prepareRound` 创建会话，只返回地址、金额、roundId 与 commitment；salt 只留在 Node 进程内。浏览器首次按 10.000000 USDC 固定额度 `approve`，之后每轮只发 `commit`；`confirmRound` 核验回执后由同地址托管演示账户等待并自动 `reveal`。
2. **结算由服务端无许可账户签名。** 浏览器在截止块后只触发服务端结算，服务端逐笔发送三个 permissionless `settle`，再汇总事实与金库变化。可选入口只用于自动结算暂时失败后的重试，不再请求用户钱包。
3. **React + wagmi 钱包层。** `getDefaultConfig` 固定单链 Arc Testnet；顶层严格按 `WagmiProvider → QueryClientProvider → RainbowKitProvider` 组合，使用深色紧凑钱包弹窗。业务组件通过 wagmi hooks 获取账户、网络、余额与钱包客户端，不自行维护注入 provider 连接状态。
4. **精度在领域层强类型化。** ERC-20 金额始终使用 `usdc6` bigint；原生 gas 始终使用 `wei18` bigint，只有展示时向上换算成六位 USDC。测试固定 `10^12` 比率和不足余额的差额文案。
5. **单屏 React 状态投影。** 六步轨根据一个 `DemoSession` 投影完成/当前/未到状态；主舞台只显示当前上下文。三张易者卡从会话开始就存在，依次从等待、推理、已应卦更新到输赢，不再另画金库卡或结算清单。
6. **哈希路由隔离卦历。** `#/oracle` 为工作台，`#/history` 为卦历和档案；使用 React 组件内的哈希路由，不引入 Next.js 或路由框架。
7. **公开配置白名单。** esbuild 只注入 `WALLETCONNECT_PROJECT_ID`、`ARC_RPC_URL`、`ARC_CHAIN_ID`、`ARC_EXPLORER`；构建脚本可读取服务端环境，但浏览器源码不能读取运行时环境。依赖为生产优化而出现的 `process.env.NODE_ENV` 字面量不等于秘密泄漏，安全门禁继续精确禁止私钥、助记词、`viem/accounts` 与账户派生 API，并扫描真实秘密值。
8. **视觉系统。** 色板只使用墨 `#0B0E14`、藏青 `#131A2A/#1A2235`、藍 `#2E4A7D`、朱 `#E24A2B`、金 `#C9A227`、白练 `#F0EDE5`；明朝体标题、宋体正文、等宽链上数据；4/8px 间距倍数、近直角边界、状态过渡 180–700ms，六爻仪式固定 6 秒。

## Error Handling

- 未检测到钱包：RainbowKit 连接弹窗列出可用钱包；没有注入钱包时给出安装指引。
- 用户拒绝：区分连接、切网、首次授权和每轮立誓，说明资金未发生该笔变动且可重试。
- 网络错误：自动尝试 `wallet_addEthereumChain` 后 `wallet_switchEthereumChain`；仍不正确则展示目标网络和 Chain ID。
- 余额不足：分别展示 ERC-20 卦金/保证金差额和原生 gas 差额，附 Circle 水龙头链接。
- 自动预测暂时失败：浏览器后台有限重试，不再要求用户点击“请三家应卦”。

## Testing

- 单元测试守住 6 位/18 位换算、余额门禁、钱包错误归类和服务端签名边界。
- 服务 API 测试覆盖准备、确认、预测与结算核验路由。
- 内容测试覆盖进度轨、单屏、独立卦历、唯一易者卡、术语清理和诚实披露。
- 真实浏览器注入无私钥 mock EIP-1193 provider，经 RainbowKit 连接后按真人节奏停顿走完桌面与移动端流程；控制台 0 错误 0 警告。

## Risks / Trade-offs

- 钱包确认弹窗仍需要用户授权，无法由页面替用户点击；“一次点击”指产品内只有“求卦”主动作，钱包安全确认仍逐笔保留。
- `reveal` 合约要求 `msg.sender == querent`；不改合约时只能让服务端持有同一受控演示账户的签名材料，任意外部钱包会在 commit 前被拒绝，避免先锁资金。
- 页面刷新会丢失尚未 reveal 的进程内 salt；旧轮到期后必须按页面给出的 `demo:recover` 路径处理，不得静默覆盖。
