# 三易第一期技术设计

完整产品与技术设计见 `docs/plans/2026-09-30-sanyi-redesign-design.md`，本文只记录影响规格的关键技术决策。

## Context

- 旧站以押注问责为核心，前端 `web/app.tsx` 单文件 1737 行，服务端同时承载問轨、賭轨、演示驱动与证据数据。
- 可复用的已验证资产：京房纳甲排盘引擎 `liuyao-chart.ts`、卦金付款核验、模型 provider、卦爻辞语料、服务端安全边界（127.0.0.1、Origin、JSON、8 KiB）。
- 约束：合约不改；继续使用 Arc 测试网；面向中文用户，境外字体服务不可用。

## Goals / Non-Goals

- Goals：统一入口；问事与八字两术；一问三家；信息真算；水墨夜视觉；去除日本元素；可复算起卦。
- Non-Goals：押注与赔付；起名、择日、星座、合婚（第一期只给引导）；一次授权额度付款（第二期）；追问、复盘与卦历（之后）；奇门参与断语。

## Decisions

1. **分类用规则而非模型**：沿用现有关键词分类思路，零成本、可测、稳定；判断不了默认问事，因为问事对任何问题都能作答。
2. **逐掷取区块**：`keccak256("sanyi-throw-v1", 付款首笔交易哈希, 区块哈希, 规范化问题, i)` 取低 3 位为三枚铜钱。付款哈希在起卦前已确定、全部输入公开，任何人可复算；区块高度严格递增防止重放。卦时取第一掷区块时间。
3. **历法双源互校**：黄历与四柱用 lunar-javascript；六爻沿用自有引擎；两者的日干支与月建必须一致，否则拒绝出结果。
4. **奇门自研 TS 实现**：运行时不引入 Python；以 kinqimen 生成的标准答案做逐字段回归。
5. **八字引擎只给事实**：格局、旺衰、用神由三家各自判断，调候表作为调候派的典籍依据入库。
6. **结构化断语＋证据核对**：统一 JSON Schema；`evidence[].ref` 只能引用服务端事实编号，`claim` 与正文中的干支六亲/十神组合必须能在事实表中找到；不通过重写一次，仍不通过不展示。
7. **梅花体用取法**：动爻集中的一卦为用；两卦都有动爻取多者、相同取下卦；无动爻下卦为用。规则写入规格并在断语中披露。
8. **变占法**：程颐的主占之辞按朱熹《易学启蒙》变占法确定性选出。
9. **生辰不落服务端**：请求随附，服务端只用于排盘，存档只存命盘。
10. **字体自托管子集化**：毛笔体只覆盖固定字表，正文用系统宋体栈。
11. **存档与凭证持久化**：`data/readings/<id>.json`，id 为 128 位随机 base32；已用付款凭证持久化，重启后仍防重用。

## Risks / Trade-offs

- 规则分类会误判边缘问题 → 标签一键改、默认问事兜底。
- 服务端选择区块存在理论上的择块空间 → 只取收到请求后的第一个新区块并公开记录；本产品为低额仪式用途。
- 模型输出长、延迟高 → 三家并行、排盘先出、逐家落笔。
- 大陆上线合规未评估 → 第一期只在测试网运行。
